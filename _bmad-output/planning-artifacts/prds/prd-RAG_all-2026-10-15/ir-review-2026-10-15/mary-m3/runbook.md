# M3 · 最小恢复动作与放行合同

日期：2026-10-15。本表是待实施验收动作，不是已执行记录。继承停写匹配备份：同 snapshot_id 的 PG／原件／解析与引用资源／非秘密配置／供应方密文；主密钥独立加密封存。没有新增常驻服务，恢复控制在现有 API 的受控维护入口与 PG 中实现。

纪元生命周期：首次部署初始化一次。普通部署／重启读取恢复 DB 之外独立持久封存的现行 epoch 与 cutover，保留有效会话和正常网络幂等；仅从备份恢复或明确安全重置生成新随机 epoch。开放前独立控制记录、DB 控制行、API／worker 进程须一致，缺失／不一致保持维护隔离，不自动重置纪元。旧进程须停用或被 DB 条件 fence，不能凭缓存的旧 epoch 写入。

## 候选与选择

| 候选 | 判定 | 原因／适用条件 |
|---|---|---|
| 恢复后清旧 token，沿用备份所有者确认权限 | 淘汰 | 旧 active／密码、旧所有者和删除状态都可能倒退，确认循环依赖旧库。 |
| PITR／同步外部安全账实现自动完整回放 | 不作为首版必需 | PITR 只到目标点；另需连续 WAL、文件匹配与独立安全账，当前无已建链路，不能承诺 RPO0。 |
| 默认隔离，最小独立安全台账＋现行受托核验，逐范围放行 | 选择 | 现有 API／PG 可承载，明确承认导出缺口；最坏情况保持隔离。 |

## 非循环信任起点

- 部署初始化独立登记恢复操作者、业务受托关系的确认渠道及 break-glass 凭据；独立介质不属于应用 DB 备份。恢复操作者身份、当前受托关系和变更依据均须可追溯，记录不能只引用旧库里的所有者／管理员字段。
- break-glass 入口仅在维护模式、受控部署通道可达，提供账号／归属／资源稳定 ID／墓碑等必要元数据及恢复动作；不提供业务查询、原件、解析正文或代登录。一次恢复结束关闭入口并轮换临时恢复凭据。
- 普通业务写入隔离期间，该入口仍允许登记经当前有权主体提出的新删除／撤权元数据，立即加 deny／墓碑并同事务写台账；不开放普通接口、不读取正文、不借维护恢复清除既有墓碑。涉及资料物理清理仍待现行受托与范围核验后才执行。
- 恢复操作者可依据独立明确受托记录重建当前业务负责人；当前业务负责人确认成员／库范围／现存资料清单。个人空间由独立核验的本人确认，停用身份不得借此自解禁；缺少可信受托或完整资料确认的范围保持隔离。确认后的正常访问仍按 FR-3／FR-4 鉴权。

## 最小安全台账

同一业务事务在 PG 中递增提交序号并记录 event_id、前一事件摘要、发生时间、动作、actor_id、target_type／稳定 ID、空间／库／资料 ID、必要的新负责人或权限变更元数据；目标 ID 永不重新分配。覆盖停用、成员移除／退出、角色／所有权变更、库撤权、用户 key 撤销、资料／库／团队删除。不得保存正文、密码、Bearer 或供应方明文 key。

导出器由现有 API 维护动作触发，将已提交连续区间与前后摘要、snapshot_id 关联、尾序号／导出时间写到独立受控介质；使用独立封存的完整性密钥认证清单。恢复时验证来源、完整性、序号连续与目标范围，再幂等重放。台账留存覆盖最旧可恢复备份至当前；淘汰备份前不得提前删掉它需要的安全事件。

**完整性验证不能证明导出后的事件不存在。** 最后导出至故障／冻结间为明确 gap；无独立现行确认时不得因导出“校验通过”宣称安全状态已完整。可由当前受托负责人重新批准明确的账号／权限／现存资料白名单，覆盖其全部范围后放行；无法形成完整清单的库继续隔离。已知删除取并集、撤权优先，恢复过程不清除 tombstone。恢复材料中缺失的正文不能靠人工确认凭空生成。

## 恢复动作顺序

| 顺序 | 执行动作／输入 | 允许推进的证据；失败分支 |
|---|---|---|
| 0 冻结 | 部署负责人关闭 Nginx 业务入口，API 只启维护模式；worker 不运行，禁外部请求，撤销旧运行进程／连接。 | 记录冻结时间、故障范围、所选恢复点、允许丢失窗口。旧生产写入者仍活跃则不得恢复同库。 |
| 1 验包 | 选匹配 snapshot_id，核对哈希清单、PG／扩展、迁移、应用版本、角色授权与文件关系；恢复分离密钥。 | 配套缺失／损坏则可见阻断；主密钥失败只报告 key_id 与错误码，不打印密文或秘密。不得调用供应方补产物。 |
| 2 换纪元 | 仅恢复／明确安全重置时用系统密码学随机源生成至少128位 recovery_id／epoch；记录 cutover UTC。恢复控制记录同时封存至独立介质，写 DB 控制行。 | 不是旧 epoch 加一；恢复标识与所有会话、key、operation／attempt 校验关联。每次恢复均重新生成，即使恢复同一包；普通重启读取现行值不换。开放前 DB／运行进程／独立记录一致，旧进程停或 fence。 |
| 3 封身份 | 删除／失效全部旧 PG Web 会话及用户只读 Bearer，所有恢复账号设 unverified，关闭正常登录和找回路径；禁用供应方调用配置。 | 禁止旧密码获取新会话、旧 key 换新 key、旧邀请自助恢复。正常 API 先通过当前 epoch 和账号核验状态；不依赖旧密码作身份核验。 |
| 4 确认受托 | 独立 break-glass 核验恢复操作者及当前业务委托，不读取旧库角色作为证明。 | 记恢复操作者／当前负责人、外部依据标识与确认时间。没有可信起点就维持隔离。 |
| 5 合并安全状态 | 验证并幂等重放台账；列明导出尾段至冻结的 gap；由当前受托负责人确认现行成员／角色、库授权与每个库的完整现存资料清单。 | account、space／KB、doc 分别有 quarantine 状态及证据；已知停用／撤权／tombstone 优先。无完整删除确认的库不可放开。候选、历史引用、下载与任务都必须查同一禁用／墓碑门槛。 |
| 6 重建凭据 | 仅对核验通过账号重置密码、按现行角色／库范围启用；按需重发只读 key；团队放行前须有一名经独立核验且当前有效的所有者。 | 放行顺序是独立操作者→现行受托关系→账号→空间／库及资料；平台恢复能力不携带正文读权。凭据可在资源仍隔离时签发，但不能绕过资源门槛。 |
| 7 隔离旧执行 | 全部旧 attempt 加恢复终止标记；回写、lease续租、结算、generation发布都须比对当前 epoch＋attempt／guard 条件。 | success 不重新计次；旧 reserved／running 生成终止为恢复中断，释放已恢复的预留且保留原桶账与 unknown 外部成本，原 key 不重跑。旧 guard 由维护恢复动作按所有者条件释放，旧 attempt 无权解新 guard。 |
| 8 对账任务与配额 | 核对已有上游 ID、真实 usage／费用和当前上海日计次；检查原件字节与全部保留／临时资产再恢复容量计量。 | 上游 ID 已知，只在该范围与对应费用动作明确授权后查询／接回原任务；无 ID 保持 unknown 待核对，不盲重交。当前日计次缺口空间冻结新增问答／对比，包括零候选完整答复，直至可信外账核对或下一上海日；不得把未知费用／计次填0。空间范围也不明则全站冻结生成。 |
| 9 验证并逐项放行 | 执行下述演练，记录允许的账号／库／资料范围；独立确认现行供应方凭据及可用 key_id；分别开启业务读、业务写、外部查询、外部付费和 worker。 | 任何外部请求在其对应范围授权前禁止发出；技术恢复权限不单独授权业务付费。只恢复本地可安全任务也需重新检查现行权限、墓碑、generation和配额，使用新 epoch／attempt；不自动重试旧生成。部分放行明确列隔离清单，不能登记为全站恢复成功。 |

## API 与重放细节

- 维护模式普通入口返回 `503 RECOVERY_QUARANTINED`；账号未核验返回 `403 IDENTITY_UNVERIFIED`；资源仍隔离返回 `423 RESOURCE_QUARANTINED`；当前日额度不确定返回 `423 QUOTA_RECONCILIATION_REQUIRED`。这些是本项目拟定错误码。资源隔离码仅向已独立核验且有该范围权限的调用者返回；未认证／无权／不存在仍走统一安全错误，不泄露资源存在；额度状态同样先核空间权限。恢复隔离统一使用 `RECOVERY_QUARANTINED`，不另设同义别名。
- 正常运行的认证元数据入口在会话／程序认证成功后，仅返回调用者自身可用的当前 epoch、server_time、cutover；不让未核验恢复账号藉此登录，也不返回他人凭据或权限清单。
- 新的计费／生成受理必须带 `X-Recovery-Epoch` 与独立 UUIDv7 `Idempotency-Key`。认证后先核 epoch：缺失／旧值返回 `409 RECOVERY_EPOCH_CHANGED`，不预留、不检索生成；即使恢复库里找不到 key 也不当新请求。对不存在的新 key，校验 UUIDv7 毫秒时间不早于本次 cutover 毫秒、不得超出服务器登记的时钟容差；否则拒绝，客户端须在获知当前 epoch／cutover／服务器时间后明确新建逻辑操作。客户端手改 epoch 不豁免旧 key 的 cutover 校验。不得自动给旧排队请求换 epoch 或换 key 重送。
- 恢复点内可确认的 success，在幂等重放有效期内可通过普通 GET operation 结果入口按原 operation_id 返回；重新核验现行身份、库权限、依赖版本和 tombstone，保留原受理时间／原上海日桶，不新检索、不重生成、不结算。过期不承诺幂等缓存无限保留，只在结果仍存在且有权时按受控会话历史读取。旧 mutating key 仍拒绝，不走“查不到就新增”。恢复点后的 success／上游 ID 若已丢失，显示不可确认，不承诺重放其结果。
- 上游状态查询是外部请求，也受范围与对应费用动作明确放行约束。查得成功仅接回当前仍有权、未删除且 attempt已由新恢复控制显式接管的文档候选；不能令被删资料或旧 generation 重新生效。查不清就停 unknown。确需新付费任务须当前有权者明确新操作，计实际新费用，不把风险埋入重试。
- 供应方恢复密文不可直接视为现行授权：须当前受托的接入管理员确认／重新输入有效凭据，必要时轮换；主密钥缺失阻断相应能力，允许已通过身份与资源门槛的本地只读验证。不得将外部 API 回包成功替代权限与资料核验。
- 对无法核对的历史成本保留 gap 和 unknown；新日开始只解除产品日配额缺口冻结，不解除身份、资料、凭据或任务隔离，也不抹去历史账。恢复中重建容量按实际保留字节，缺文件先阻断相关资源，不预先返还容量。

## 最小演练断言

| 演练 | 必须留下的可观察证据 |
|---|---|
| 备份后停用／移除／撤权／撤 key／删除，恢复旧点 | 旧密码无法登录，旧 Cookie／Bearer 失败；旧成员、旧负责人、仅平台恢复者无法读正文；删文档在检索／历史／引用／下载／迟到候选均不可访问。 |
| 台账尾段缺失、旧所有者被移除 | 无独立现行委托不能自证；未确认账号／库不放行；已知墓碑不因恢复人工放行被擦除。 |
| 丢失同日 operation＋重放旧 epoch／key＋迟到 worker | 受理前拒旧 epoch，旧 key 查无也不建新 operation；当天生成被冻结；旧执行零发布、零重复产品结算，无授权时外部请求计数为0。 |
| 上游已接收、jobid丢失；主密钥缺失 | unknown 与密钥阻断可见；不自动重交、不输出秘密；有 ID 的状态查询也必须先授权。 |
| 同包连续恢复两次、恢复 point 内 success | 两次 epoch 不同，第一轮新凭据在第二轮失效；历史 success 仅当前授权后原样读取，原时间／版本／日桶保留且无新调用。 |

恢复负责人保存 snapshot_id、恢复点、实际数据丢失／安全台账 gap、各放行范围、依据标识、确认人／操作人、epoch、各类任务与对账状态、演练结果和仍隔离清单。首版上线前完成一次干净隔离环境演练；备份存在、进程启动或引用偶然可开都不等于通过。
